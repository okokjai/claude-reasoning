# Contract C2: Inter-Stage Transfer Contract

**Defines the "mandatory transfer fields" and "optional transfer fields" for each stage, ensuring data integrity across stages.**

| Transfer Direction | Mandatory Fields | Optional Fields |
|--------------------|------------------|-----------------|
| A1 -> A0 | `data_type`, `primary_domain` | `sub_question_types`, `specified_mode` |
| A0 -> A2 | `primary_mode`, `route_rule`, `route_confidence` | -- |
| A1 -> A2 | `data_type`, `primary_domain` | `secondary_domains`, `trigger_reason` |
| A2 -> Stage 0 | `primary_mode`, `scale`, `platform_mode`, `can_branch` | `primary_domain` (ambient from A1), `disclaimer_text`, `evidence_cap`, `quality_cap` |
| C0 -> Stage 0 | `user_constraints`, `implicit_assumptions`, `success_criteria` | -- |
| A1 -> Stage 0 | `primary_domain` (ambient) | `secondary_domains` |
| Stage 0 -> Stage 1 | `brainstorm_packet` | -- |
| A2 -> Stage 1 | `primary_mode`, `scale`, `platform_mode`, `can_branch` | `disclaimer_text`, `evidence_cap`, `quality_cap` |
| A2 -> Stage 3 | `verification_paths` | -- |
| A2 -> Stage 5 | `primary_mode`, `primary_domain`, `scale`, `can_branch`, `stage_0_revision_count` | -- |
| A1 -> Stage 1 | `primary_domain`, `data_type` | `secondary_domains` |
| C0 -> Stage 1 | `user_constraints`, `success_criteria`, `implicit_assumptions` | -- |
| C1 -> Stage 6 | `fallback_mode`, `skip_compensation` | `skippable_stages` |
| Stage 1 -> Stage 2 | `core_problem`, `sub_problems`, `known_facts`, `immutable_constraints` | `unknown_facts`, `sequential_branches` |
| Stage 2 -> Stage 3 | `verification_plan`, `hypotheses`, `claim_registry`, `search_paths_required`, `negative_search_queries` | `null_hypothesis`, `most_dangerous_hypothesis` |
| Stage 3 -> Stage 4 | `evidence_matrix`, `cross_validation`, `evidence_quality`, `source_quality_matrix`, `claim_verification_status`, `data_gap_list`, `claim_registry` | `unverified_hypotheses`, `tool_calls` |
| Stage 4 -> Stage 5 | `preliminary_conclusion`, `confirmed_facts`, `residual_uncertainty`, `source_quality_matrix`, `claim_verification_status`, `data_gap_list`, `claim_registry` | `contradictory_evidence_ref`, `domain_specific_analysis` |
| Stage 1 -> Stage 0 | `framing_revision_request` (top-level return payload) | only when the Stage 0/Stage 1 handoff is materially invalid and `stage_0_revision_count < 1` |
| Stage 5 -> Stage 0 | `framing_revision_request` (top-level return payload) | only when problem framing is invalid and `stage_0_revision_count < 1` |
| Stage 5 -> Stage 1 | `fix_requirements`, `revision_branches` (decomposition-mismatch record) | only when the problem definition remains valid, the defect is a decomposition mismatch, and `revision_target=stage-1` |
| Stage 5 -> Stage 2 | `fix_requirements`, `revision_branches` (hypothesis revision record) | only when the defect is a hypothesis defect, `revision_target=stage-2`, and it is not a framing defect |
| Stage 5 -> Stage 3 | `fix_requirements`, `revision_branches` (evidence revision record) | only when the defect is an evidence defect, `revision_target=stage-3`, and it is not a framing defect |
| Stage 3 -> Stage 2 | `needs_revision=yes`, `unverified_hypotheses`, `evidence_matrix`, `claim_registry` (only when all candidate entities fail existence verification; bounded rerun, does not create new hypotheses beyond retry limit) | `failure_context` |
| Stage 5 -> Stage 5.5 | `preliminary_conclusion`, `evidence_matrix`, `source_quality_matrix`, `claim_registry`, `scale`, `primary_domain` (control flow: only enters when `needs_revision=no`) | `failure_context` |
| Stage 3 -> Stage 5.5 | `evidence_matrix`, `source_quality_matrix`, `claim_registry` | -- |
| Stage 5.5 -> Stage 3 | `failure_route=stage-3`, `failure_context` (affected claims, failure reason, required changes, and current evidence/registry snapshot) when entity/source/evidence or missing cross-reference evidence fails | -- |
| Stage 5.5 -> Stage 5 | `failure_route=stage-5`, `failure_context` (affected claims, failure reason, required changes, and current evidence/registry snapshot) when evidence exists but conclusion wording, precision, annotation, or concealed conflict must be revised | -- |
| Stage 5.5 -> Stage 6 | `hallucination_pass`, `hallucination_fail_reason` | -- |
| Stage 5 -> Stage 6 | `preliminary_conclusion`, `fix_requirements`, `needs_revision`, `precision_audit`, `confidence_table` (each entry `{claim, source_tier, cross_validation_count, confidence, notes}`) | `revision_branches`, `price_notes` |
| A2 -> Stage 6 | `evidence_cap`, `quality_cap`, `platform_mode` | `disclaimer_text` |
| Stage 6 -> Stage 1 | `fix_requirements`, `gate_failure_class`, `revision_count` | only for post-Stage-5.5 conclusion gate failure requiring decomposition correction; `revision_count` starts at `0`, is owned by orchestration, increments on this return, and no second return is allowed |
| Stage 6 -> Quality Self-Assessment | `logic_closed`, `evidence_sufficient`, `hallucination_clean`, `hypothesis_count` (ambient from A2), `primary_domain` (ambient from A1) | `confidence`, `conclusion` |
| Quality Self-Assessment -> Memory | `verdict`, `total_score`, `denominator` | `reasoning_log`, `pattern_asset`, `precision_issues` |

`precision_score` is an output of Quality, not an input transfer field.

The legacy alias `stage_0_uncertainty` is forbidden and is not a transfer field. The canonical uncertainty/framing fields are inside `brainstorm_packet`.

**Execution Rules**:
1. Every reasoning task receives a C0-shaped context packet before mandatory Stage 0. Run C0 when its trigger applies; otherwise provide `user_constraints: []`, `implicit_assumptions: []`, and `success_criteria: []` as explicit defaults. `raw_question` and `primary_domain` come from ambient A1/user context and are not transferred through C0.
2. Stage 0 is mandatory for reasoning tasks after the C0-shaped context packet and A2, and before Stage 1; its `brainstorm_packet` is a candidate input, not evidence, and cannot register claims or bypass verification, hallucination, or quality gates. `brainstorm_packet.framing_status`, `brainstorm_packet.hidden_constraints`, and `brainstorm_packet.frame_comparison` are the canonical Stage 0 uncertainty/framing fields; no parallel `stage_0_uncertainty` transfer field exists.
3. The run-level `stage_0_revision_count` is owned by the orchestration layer, starts at `0`, increments exactly when Stage 5 or Stage 1 returns to Stage 0, and is bounded to `0..1`. If it is already `1`, do not re-enter Stage 0; terminate the framing-revision route and record the unresolved framing issue. This counter is distinct from Stage 0 B9's internal `iteration_count`.
4. Before each stage begins, check that all "mandatory fields" from the previous stage's output are complete.
5. Missing mandatory fields -> return to the previous stage to fill them in; a missing `brainstorm_packet` returns to Stage 0.
6. A Stage 1 decomposition mismatch is a conditional `handoff_issue` with shape `{kind: material-framing-mismatch, summary, affected_fields, materiality, route: Stage 0 | Stage 1, framing_revision_request_record}`. The top-level `framing_revision_request` output record is defined below; the nested `framing_revision_request_record` is only a reference to that record, not a second field path. Route to Stage 0 only when the framing is invalid; otherwise route to Stage 1 when the framing is valid but decomposition is invalid. A Stage 0 return increments `stage_0_revision_count` and is blocked when the count is already `1`.
7. Stage 5 conditional routes are mutually exclusive by defect class: a framing defect routes only to Stage 0 when `stage_0_revision_count < 1`; a valid-problem-definition decomposition mismatch routes to Stage 1; a hypothesis defect routes to Stage 2; and an evidence defect routes to Stage 3. Never route a framing defect to Stage 2 or Stage 3 because its consequences appear there. Stage 5.5 failures use `failure_route=stage-3` or `failure_route=stage-5` with `failure_context`; Stage 6 gate failures use the bounded Stage 6 -> Stage 1 route only after Stage 5.5 has passed. Each backward route carries `fix_requirements` and the records appropriate to its target. When no permitted route remains, use `revision_target=none` and record the issue in `residual_uncertainty`.
8. `framing_revision_request` is a top-level return payload on Stage 0-directed Stage 1 and Stage 5 outputs with shape `{reason, affected_fields, invalid_frame, requested_change, stage_0_revision_count}`. A Stage 1 `handoff_issue` or Stage 5 framing `revision_branches` entry may include `framing_revision_request_record` only as an explicitly named reference to that top-level record.
9. Missing optional fields do not block the flow, but mark it in the Reasoning Log.
